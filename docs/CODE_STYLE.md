# Архитектура и Стиль кода (OOP & SOLID)

В этом проекте действуют строгие правила по написанию чистого, компактного и объектно-ориентированного кода.

## 1. Архитектурные принципы
* **ООП и SOLID**: Код должен быть написан с максимальным использованием принципов SOLID. Следует избегать процедурного программирования (линейных портянок кода). Разделяйте логику по ответственности (Single Responsibility Principle) — если метод берет на себя слишком много, выделяйте логику в небольшие приватные методы-помощники.
* **Лаконичность и отказ от лишних переменных**: Если переменная используется всего один раз, не создавайте ее отдельно. Инлайните выражения прямо в местах использования (например, прямо в условие `if($var = ...)`). Код должен быть максимально чистым и читаться как текст.
* **Отказ от `in_array()` и `empty()`**: Запрещено использовать функции `in_array()` и `empty()` из-за их нагруженности и итеративного подхода (`O(n)` перебор). Вместо `in_array()` используйте `O(1)` проверку по ключам ассоциативного массива через `isset($items[$key])`, а вместо `empty($var)` — прямую булеву проверку `!$var` или `isset()`.
* **Разделение операционного действия и проверки результата (Обособление интерактивных объектов и массивов, отказ от двойных скобок `((` и прямого разыменования `)['key']`)**: Важно отделять само операционное действие (например, выполнение запроса и получение объекта ответа `Response`, декодирование JSON, подключение файла миграции, открытие сокета, извлечение опции) от последующей работы с этим объектом/массивом или передачи его в функции/методы проверки. Избегайте нескольких подряд открывающихся круглых скобок `((` там, где это возможно (если технически без `((` никак не обойтись — не возбраняется). Если функция или метод возвращает массив, запрещено обращаться к его ключам напрямую на вызове (`func(...)['key']`) — сначала присвойте результат переменной, и уже затем обращайтесь к ключу (`$result['key']`). Если внутри скобок `(` переменной или свойству присваивается значение, у которого тут же вызывается метод, либо оно передается аргументом в функцию или сравнивается через дополнительные скобки — выносите операцию получения объекта/значения перед условием (можно на той же строке через `;`).
  * *Неправильно*: `if(($response = $this->get('models', ['curl' => [CURLOPT_RESOLVE => ['openrouter.ai:443:['.$ip.']']]]))->getStatusCode() === 200) return $response;`
  * *Правильно*: `$response = $this->get('models', ['curl' => [CURLOPT_RESOLVE => ['openrouter.ai:443:['.$ip.']']]]); if($response->getStatusCode() === 200) return $response;`
  * *Неправильно*: `json_decode($response->getBody(), true, 512, JSON_BIGINT_AS_STRING)['data']`
  * *Правильно*: `$result = json_decode($response->getBody(), true, 512, JSON_BIGINT_AS_STRING);` и затем `$result['data']`
  * *Исключение*: Прямые fluent-цепочки вызова без промежуточного присваивания и проверки состояния (например, `$this->container->get($class)->build($this)->dispatch($this->getOption($option));`) допускаются в одну цепочку без разбиения на временные переменные.
* **Упрощение нейминга (Лаконичные однословные имена вместо избыточного `camelCase`)**: Избегайте составных `camelCase`-имён везде (в методах, переменных, свойствах, ключах), где смысл однозначно передаётся одним словом, близким к сути реализации (например: `csrf` вместо `extractCsrf`, `catalog` вместо `parseCatalog`, `rss` вместо `parseRss`, `description` вместо `extractDescription`, `preview` вместо `checkPreview`, `hash` вместо `makeHash`, `clean` вместо `cleanText`). Если однословное имя вызывает сомнения или неоднозначность, использование префиксов действий или «венгерской нотации» не возбраняется.
* **Строгое разделение слоёв `Magistrale` и `App` (однонаправленная зависимость)**:
  * В слое **`Magistrale` (`src/Magistrale/`)** размещаются исключительно широкие, переиспользуемые и инфраструктурные реализации (контракты, провайдеры, базовые инфлекторы, трейты, HTTP-клиенты, драйверы агентов, логгеры и система миграций БД). **Внутри `src/Magistrale/` категорически запрещено использовать или импортировать любые классы из неймспейса `App\`**.
  * В слое **`App` (`src/App/`)** размещается вся прикладная бизнес-логика проекта (контроллеры, MCP-инструменты, модели предметной области, прикладные диспетчеры, миксины, операторы, стратегии и профильные инфлекторы). **Внутри `src/App/` использование контрактов, трейтов, клиентов и базовых классов из `Magistrale\` активно приветствуется** (`App` зависит от `Magistrale`, но `Magistrale` никогда не знает об `App`).
* **Единый контур перехвата исключений (`try / catch`)**: Если метод или цепочка вызовов уже обёрнуты в родительский блок `try / catch(Throwable)`, запрещено плодить внутри него вложенные `try / catch`, подавлять ошибки через `@` или нагромождать избыточные защитные проверки (`??`, `isset`, `file_exists`, `method_exists` и т.д.), пытаясь вручную обойти выброс `Throwable` (`TypeError`, `ErrorException`, `ValueError` и т.д.). Код должен оставаться максимально чистым и прямолинейным: пусть исключение свободно выбрасывается — оно штатно перехватится и залогируется на верхнем уровне `try / catch` (настройка `'http_errors' => false` для Guzzle не в счёт).
* **Доверие спецификации ответов и точечное применение `array.get` (Отказ от защитных `?? null` / `?? []`)**: При разборе внешних структур данных (JSON API, `HH-Lux-InitialState`, XML, внутренних конфигов) запрещено оборачивать гарантированные спецификацией ключи в защитные `?? null`, `?? []`, `?? 0` или `array.get`. Если внешняя спецификация источника изменится и базовое поле пропадёт, код **обязан** выбросить исключение, которое перехватится верхним `try / catch(Throwable)` и уведомит администратора через `TelegramObserver` о смене контракта. Хелпер `$this->callback->array('get', ...)` применяется **исключительно** для тех вложенных полей, которые легитимно могут отсутствовать по предметной логике самого источника в штатном ответе (например, опциональный уличный адрес `address.displayName` при обязательном `area.name`, необязательный массив графиков `workFormats.0.workFormatsElement` или опциональная ветка `vacancyView.vacancyFull.vacancy`).
* **Трёхуровневая формула декомпозиции (Миксины → Колбэки/Операторы → `Abstract*` + Конкретные классы)**: При проектировании и планировании любой новой функциональности изначально закладывайте разделение ответственности по трём уровням:
  1. **Миксины (`MacroableInterface` + `MixinInterface` в `definitions/mixins.php`) — Слой работы с «сырыми» данными**: Вся низкоуровневая обработка данных (парсинг и сборка HTML/XML/JSON, регулярные выражения `preg_match` / `preg_replace`, `htmlspecialchars`, `addcslashes`, расчёт хешей, сборка RESP-фреймов, подготовка SQL-байндингов, приведение `Throwable` или смешанных типов к строке через `prepare()`) выносится исключительно в классы-миксины (`src/Magistrale/Mixins/*Mixin.php` и `src/App/Mixins/*Mixin.php`). Внутри миксинов запрещены сетевые вызовы и управление бизнес-потоком; в начале каждого замыкания с обращением к `$this->` указывается PHPDoc `/** @var ЦелевойКласс $this */`.
  2. **Колбэки, Операторы и Хелперы (`OperableInterface` + `CallbackInterface` + `OperatorInterface`) — Слой операционных конвейеров (`pipe`)**: Операционные действия (вызовы методов `$this->client`, последовательные шаги трансформации и отправки) и универсальные хелперы (`definitions/helpers.php`, такие как `ArrayHelper`) реализуют `OperatorInterface` и связываются с методами миксинов в декларативные конвейеры внутри `CallbackInterface` через `CallbackInflector` (где выход предыдущего замыкания автоматически передаётся аргументом в следующее со строгой типизацией, например `fn(mixed $payload) => $this->prepare($payload)` → `fn(string $payload) => $this->client->notify($payload)`). Компактные конвейеры (1–2 шага) регистрируются напрямую в методе `setCallback(CallbackInterface $callback)` на уровне `Abstract*` или целевого класса (как в `AbstractObserver` и `OpenRouterDispatcher`), а разветвлённые мульти-пайплайны выносятся в отдельные классы `*Operator` (`definitions/operators.php`, как `FLOperator`, `HHOperator` и `MigrateOperator`).
  3. **Уровень `Abstract*` и конкретных реализаций (`*Dispatcher`, `*Observer`, `*Command`)**: Общий конструктор `__construct(...)`, базовые зависимости (`Client`, `LoggerInterface`, `Capsule`), подключение трейтов (`MacroableTrait`, `OperableTrait`, `ObservableTrait`) и общая настройка `setCallback()` всегда выносятся на уровень родительского `Abstract*` своего слоя (`App` или `Magistrale`). В конкретном дочернем классе (например, `TelegramObserver`, `PublishDispatcher`, `FLDispatcher`, `HHDispatcher`) не должно быть конструктора и «сырой» обработки данных — только чистый метод исполнения (`dispatch()` / `update()`), вызывающий конвейер `$this->callback->...`, выбрасывающий `RuntimeException` при неуспехе и перехватывающий все сбои в едином блоке `catch(Throwable $e)` с логированием и уведомлением наблюдателя (`$this->observer->update($e)`).
  * *Неправильно*: `$value = $input->getOption($option); if($value !== false) { ... $dispatcher->dispatch($value === true ? null : $value); }`
  * *Правильно*: `if($this->hasOption($option)) { $this->container->get($class)->build($this)->dispatch($this->getOption($option)); return Command::SUCCESS; }`
* **Паттерны ООП**: Смело задействуйте классические паттерны проектирования (где это уместно), чтобы код был гибким и легко расширяемым.
* **Максимальное использование DI-контейнера вместо дублирования конструкторов**: При проектировании и планировании новой функциональности приоритетом является использование возможностей DI-контейнера (`League\Container`, `Magistrale\Providers\*` + карты в `definitions/*.php` и `Magistrale\Inflectors\*` / `App\Inflectors\*`). Запрещено нагромождать дочерние классы однотипными конструкторами (`__construct` с `parent::__construct(...)`) только ради проброса разных конкретных реализаций одной зависимости (например, разных наследников `AbstractClient`). Общий конструктор с базовым типом/интерфейсом должен объявляться один раз в абстрактном родителе (`Abstract*`), а связывание конкретных зависимостей для каждого подкласса делегируется сервис-провайдеру или инфлектору и конфигурационным файлам `definitions/*.php`.
* **`BootableServiceProviderInterface` для сервис-провайдеров**: Все сервис-провайдеры (`AbstractProvider`), в которых есть получение настроек или определений через `$this->container()->get(...)`, обязаны реализовывать интерфейс `League\Container\ServiceProvider\BootableServiceProviderInterface`, извлекать конфигурацию в приватное свойство класса внутри метода `boot(): void` (по примеру `McpServiceProvider`), и уже это свойство использовать внутри `register(): void`.

## 2. Форматирование кода
* **Пробелы**: Не ставьте пробел после управляющих конструкций (`if`, `while`, `foreach`, `catch` и т.д.).
  * *Пример*: `if($condition)`
* **Фигурные скобки**: Открывающая фигурная скобка `{` для тел операторов (включая `try`/`catch`) должна переноситься на новую строку.
  * *Пример*:
    ```php
    if($condition)
    {
        // ...
    }
    ```
* **Длина строки**: Не переносите код на новую строку, если он помещается в одну линию (лимит длины строки — **220 символов**). Делайте переносы только в случае превышения этого лимита.
* **Кавычки**: Двойные кавычки (`"`) в PHP-коде — моветон, их быть не должно. Всегда используйте одинарные кавычки (`'`) и конкатенацию через точку (`.`) без пробелов (а для символов перевода строки — константу `PHP_EOL`).
* **Конкатенация строк**: Запрещено ставить пробелы вокруг оператора точки (`.`) при соединении строк с переменными, свойствами класса, константами или вызовами функций.
  * *Неправильно*: `'Привет ' . $name` или `"Привет {$name}"`
  * *Правильно*: `'Привет '.$name`
* **Атрибуты и константы класса (порядок и отступы)**: В начале класса соблюдается строгий порядок объявления: сначала идут **статические атрибуты**, затем **обычные атрибуты**, затем **константы**. Между всеми атрибутами и константами класса обязательно ставится пустая строка (двойной разрыв строки).
  * *Неправильно*:
    ```php
    private array $options;
    private string $homeDir = '';
    ```
  * *Правильно*:
    ```php
    private array $options;

    private string $homeDir = '';
    ```

## 3. Импорты и группировка (Блок `use`)
* **Чистка неиспользуемых импортов**: Удаляйте все неиспользуемые импорты (`use`) из верхней части файлов.
* **Использование `use` вместо inline-неймспейсов**: Запрещено использовать длинные полные имена классов внутри кода (например, `new \Cli\Commands\MigrateCommand()`). Выносите такие классы в блок `use` вверху файла и пишите только короткое имя: `new MigrateCommand()`.
* **Группировка по последнему слешу**: Если у импортируемых классов совпадает вся часть пространства имён до последнего слеша, объединяйте их в одну инструкцию с помощью фигурных скобок `{}`.
  * *Пример*:
    ```php
    use App\Tools\{PingTool, PublishTool, DeleteTool, DeleteByTextTool};
    ```
